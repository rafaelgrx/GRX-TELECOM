Guia de publicação e operação

GRX Telecom · versão 2.0 · revisão de 02/11/2026

Entrega: aplicativo estático revisado para celular e desktop, pronto para publicar em HTTPS. A configuração padrão é local. O modo equipe só deve ser ativado após configurar autenticação e permissões no Supabase.

Antes de atualizar: exporte um backup no sistema antigo em cada aparelho. Não limpe os dados do navegador, não altere o domínio antes de salvar os backups e não execute a migração em produção sem conferir os comprovantes. Não há garantia de “100% sem erros”; veja os resultados e limites em Relatório de testes.

1. Publicar no GitHub Pages

Descompacte o ZIP. Envie o conteúdo da pasta para a raiz do repositório, mantendo a pasta vendor e os nomes dos arquivos. Os arquivos essenciais são index.html, config.js, sw.js, manifest.webmanifest, os ícones e .nojekyll. Não envie somente index.html: esta versão tem dependências locais para dispensar CDN.

No repositório: Settings → Pages → Deploy from a branch → main → / (root) → Save. Abra o endereço HTTPS fornecido pelo GitHub. Não use o visualizador de arquivos ou file:// para homologar armazenamento, senhas e PWA. Nenhuma publicação na sua conta foi feita nesta entrega.

2. Modo local

Deixe url e anonKey vazias em config.js. No primeiro acesso, defina uma senha de 8 a 128 caracteres para rafael@grxtelecom.com.br. O formulário de criação deixa de estar disponível após configurar o administrador. Os hashes da versão anterior continuam aceitos; novas senhas locais usam PBKDF2-SHA256 com salt aleatório e 600 mil iterações. Não existe senha padrão embutida.

O acesso local é apenas uma barreira de interface: alguém com acesso ao navegador pode ler ou alterar os dados locais. Os lançamentos ficam no localStorage; fotos ficam no IndexedDB. O login local não é sincronizado com os outros aparelhos. Limpar dados do site, trocar domínio ou perder o aparelho pode apagar essa base. Exporte backups e guarde-os fora do dispositivo.

A atualização no mesmo endereço mantém as chaves locais antigas. Em um novo endereço, primeiro configure uma conta e importe o backup. As contas e senhas do backup não são restauradas, para evitar substituir permissões existentes. Em caso de senha local esquecida, não há redefinição pública: a recuperação exige procedimento controlado e backup. A senha da nuvem pode ser redefinida pelo administrador no Supabase.

3. Nuvem segura da equipe

O modelo é para uma equipe por projeto Supabase. Todos os membros autorizados podem consultar os lançamentos da equipe. Cada membro pode alterar os próprios lançamentos; o administrador pode alterar qualquer lançamento e os cadastros compartilhados. Nenhum cliente pode conceder privilégios de administrador.

  1. Crie um projeto Supabase e revise região, limites e política de backups de acordo com sua necessidade. Não inclua chave service_role, secret key ou senha de banco em arquivos públicos.
  2. Em um projeto de teste, execute supabase.sql completo no SQL Editor. O script cria novas tabelas v2, lista de membros, revisão de registros e bucket privado. O script também revoga o acesso de clientes às tabelas legadas grx_regs/grx_config e torna o bucket legado privado, sem apagar seu conteúdo. Isso desativa o acesso API do app antigo. Faça a cópia de segurança e planeje a janela de migração antes de aplicar ao projeto existente.
  3. Authentication → Users → Add/Create user: crie a conta de rafael@grxtelecom.com.br, com e-mail confirmado e senha segura. Não dependa do formulário local: ele fica desativado no modo nuvem. Desative inscrições públicas de usuários nas configurações de Auth.
  4. Autorize o administrador no SQL Editor:
insert into public.grx_members(user_id,email,admin)
select id,lower(email),true from auth.users
where lower(email)='rafael@grxtelecom.com.br'
on conflict(user_id) do update
set email=excluded.email,admin=true,active=true;

Para cada colaborador, crie a conta em Authentication e repita o comando com o e-mail dele e admin=false. Não cadastre contas da equipe apenas no modo local. Para revogar o acesso, marque active=false em grx_members. A revogação bloqueia novas operações no servidor; não apaga cópias já armazenadas em aparelhos.

  1. Preencha url com a Project URL HTTPS e anonKey com a chave pública/publishable ou anon do projeto em config.js. Preserve os nomes v2 de tabela e bucket. Configuração parcial falha fechada e não libera login local como substituto.
  2. Publique os arquivos atualizados. Se o site já tiver um service worker, atualize também o identificador CACHE em sw.js. Depois aplique a atualização quando não houver formulário aberto. O código do app e a configuração são armazenados juntos para evitar versões misturadas.
  3. Faça login com a conta criada no Auth. Em Cadastros, confirme “Nuvem verificada”, salve um lançamento com foto e use outro aparelho para conferir o registro e ampliar o comprovante. Teste também excluir e editar.

O SQL usa Auth, associação de membros e Row Level Security. As fotos não têm URL pública: o app solicita links temporários assinados. As permissões e o bucket devem ser conferidos no projeto real. Referências: Storage e RLS e login com e-mail e senha.

4. Migrar dados antigos sem misturar bases

O modo nuvem tem armazenamento local separado do modo local, por projeto. Ativar chaves não envia automaticamente dados antigos. Exporte o backup completo com fotos no sistema de origem antes de fechar o acesso às tabelas/bucket antigos. Confira se o arquivo contém fotos e se não há missingPhotos. Em seguida, entre como admin no modo nuvem, importe, confira os totais e use Enviar tudo. A importação substitui a base local; não apaga automaticamente dados do servidor.

Backups v1 da versão anterior são aceitos se os lançamentos e as fotos estiverem íntegros. Migrações entre projetos descartam os caminhos de foto e as revisões de servidor de origem, exigem as imagens dentro do backup e reenviam os comprovantes para o bucket de destino. Se um arquivo antigo estiver incompleto, a importação para e explica o problema, sem trocar sua base.

5. Uso diário e falhas de conexão

O aplicativo permite criar, editar e excluir lançamentos com confirmação. Valores aceitos incluem 123,45, 1.234,56 e 123.45. O valor 1.234 é interpretado como mil duzentos e trinta e quatro no padrão pt-BR. KM aceita 123456 ou 123.456, sem casas decimais. Valores negativos, notação científica e formatos inválidos são recusados.

As fotos são reduzidas a até 1600 px, JPEG qualidade 0,75. Arquivos de entrada limitados a 20 MB e comprovantes armazenados limitados a 6 MB. HEIC depende do navegador: converta para JPEG se necessário. Salvar aguarda o processamento do comprovante; quando a gravação falha, o formulário é preservado.

Os lançamentos pendentes são persistidos antes do envio. A foto precisa ser enviada antes de confirmar o registro. Falha não recebe o status de enviado. Ao recuperar conexão ou tocar Sincronizar, o app tenta novamente. Cadastros alterados pelo administrador também ficam pendentes se a gravação remota falhar.

Alterações concorrentes de lançamentos usam revisão otimista. O app não sobrescreve silenciosamente uma revisão mais nova. Use “Rever conflito”, compare as versões e escolha a da nuvem ou confirme o reenvio da sua versão. Exporte um backup antes de descartar uma alteração. A configuração de listas compartilhadas deve ter um responsável por vez: não existe resolução de conflito campo a campo para dois administradores alterando listas simultaneamente.

As exclusões na nuvem usam marcadores persistentes para não reaparecerem em outros aparelhos. As fotos antigas, substituídas ou vinculadas a registros excluídos não são eliminadas automaticamente do bucket. Um administrador deve revisar retenção e quota periodicamente, por procedimento controlado. Não remova marcadores de exclusão antes de migrar todos os aparelhos.

6. Offline e instalação

A primeira abertura deve ocorrer online em HTTPS. O service worker guarda apenas arquivos do aplicativo, nunca respostas de Auth, banco ou Storage. O teste confirmou recarga offline no modo local com foto em cache e novo lançamento sem conexão. O navegador pode oferecer “Instalar aplicativo” ou “Adicionar à tela de início”; disponibilidade depende do sistema.

No modo nuvem, o primeiro login e a validação do membro exigem internet. Uma sessão já validada pode abrir offline usando identidade e permissões em cache somente enquanto o prazo da sessão guardada ainda for válido; depois é necessário reconectar. Só comprovantes efetivamente baixados ficam disponíveis sem sinal. O pré-carregamento é limitado a 80 fotos por rodada; o backup tenta buscar todos os comprovantes e informa os indisponíveis. O cache offline da nuvem não foi homologado em aparelhos físicos.

Antes de atualizar o app, salve ou limpe os formulários. O botão de atualização não aplica a nova versão durante gravação, edição ou formulário com conteúdo. Em futuras atualizações, altere o nome CACHE em sw.js para criar uma versão nova. Não limpe IndexedDB/localStorage para atualizar.

7. Relatórios e backups

Consulta permite filtrar por período, veículo, cidade, usuário, pagamento e tipo, inclusive valores históricos de cadastros removidos. CSV usa separador ponto e vírgula e contém veículo, serviços/categoria, KM e valor. CSV não é uma planilha XLSX. O botão PDF abre a impressão do navegador: escolha “Salvar como PDF”. WhatsApp abre uma mensagem de resumo com até 15 itens, total e aviso de itens adicionais.

O backup JSON leva lançamentos, cadastros e comprovantes disponíveis, mas não hashes de senha. Guarde-o em local protegido, pois contém dados da equipe e fotos. Se houver missingPhotos, o backup não está completo: reconecte, baixe as fotos e gere outro. Antes de restaurar, a importação valida formato, IDs duplicados, valores, cadastros e fotos; uma falha de quota preserva a base anterior em condições normais de execução. Nenhum armazenamento de navegador é uma transação distribuída contra queda brusca de energia.

8. Homologação antes do uso com dados reais

Verifique no projeto final: login e revogação de membro; leitura e foto em dois aparelhos; falha de rede durante upload; recarga sem sinal; edição concorrente; exclusão; backup e restauração; impressão; câmera e galeria em Android e iPhone. Confira políticas pelo painel Supabase e não reative as políticas abertas da versão antiga. Faça uma implantação piloto com poucos registros e só então migre a equipe.

A senha local não é criptografia de disco. As fotos armazenadas no navegador não são criptografadas pelo aplicativo. Use bloqueio do aparelho, perfil individual de navegador e backups protegidos. O app não é solução multiempresa, sistema fiscal nem livro contábil certificado.

9. Testes reproduzíveis para suporte técnico

Os testes e os resultados estão na pasta tests. Requisitos: Node.js atual e navegadores Playwright. Em uma cópia de teste, com config.js vazio, execute npm install, depois npx playwright install chromium firefox. Em Linux podem ser necessárias dependências do sistema via npx playwright install-deps. Em um terminal rode npm run serve; em outro, npm test. A porta localhost:8765 precisa estar livre. Não execute testes no site de produção.

A versão do SDK Supabase está fixada e incluída localmente em vendor; sua licença está em SUPABASE-LICENSE.txt. Novas versões do SDK exigem nova regressão. Consulte os resultados e limites completos da validação.
